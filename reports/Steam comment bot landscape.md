# Desktop Steam comment bot has no competition

The mass Steam profile engagement space is overwhelmingly terminal-only, and the leader — **3urobeat/steam-comment-service-bot** (Node.js, GPL-3.0, 358 stars, "mass coordinated comments/likes/favs/follows" controlled from terminal and Steam Chat) ([GitHub](https://github.com/3urobeat/steam-comment-service-bot)) — has no desktop GUI fork, only an in-development Vue web frontend by DerDeathraven served over a REST-API plugin ([frontend](https://github.com/DerDeathraven/steam-comment-service-bot-frontend); [REST plugin](https://github.com/DerDeathraven/steam-comment-bot-rest-api)). The commercial side is a long tail of Discord-bot-fed Steam-group storefronts (Boost Comments LLC at €40/1000, boosting-service.cloud, imbaboost.com) with frequent non-delivery complaints on Trustpilot and no self-serve dashboards or desktop apps ([Trustpilot](https://uk.trustpilot.com/review/boosting-service.com)). Steam's post-2023 `IAuthenticationService` login flow is captcha-free in practice — libraries hit it directly and surface Steam Guard challenges instead of solvable images ([pkg.go.dev escrow-tf/steam](https://pkg.go.dev/github.com/escrow-tf/steam/api/auth)) — so the real operational problems are rate limits (per-IP HTTP 429 and per-account "posting too frequently", with community-reported ceilings around 200 comments/account/day) and the plumbing of maFile-based Steam Guard mobile confirmations. For a desktop port of 3urobeat's bot the cleanest architecture is an **Electron shell (or Tauri with a Node sidecar) that keeps the existing Node.js engine intact** and consumes it either in-process or over the already-shipping REST API plugin — a market slot nobody currently occupies.

## 3urobeat owns an uncontested niche because nobody else does likes/favs/follows

The GitHub `steam-bot` topic surfaces 57 repos, and in the 20 visible on the first page only **3urobeat/steam-comment-service-bot explicitly advertises "mass coordinated comments/likes/favs/follows"** as a single integrated feature ([topic page](https://github.com/topics/steam-bot); [repo](https://github.com/3urobeat/steam-comment-service-bot)). The rest cleave into three camps that do not overlap: **card/hour farming** (ArchiSteamFarm at 13.8k stars and 14,639 commits is the giant here, but its feature list is card farming, trading, keys, SteamGuard — not commenting or liking ([ArchiSteamFarm](https://github.com/JustArchiNET/ArchiSteamFarm))), **trading bots** (prasunroy/steam-bot, the older C# SteamBot family), and **CS:GO reports** (Marc3842h/Titan, 202 stars, archived April 2026 ([Titan](https://github.com/Marc3842h/Titan))). The one adjacent Python repo, czQery/steam-comment-bot, has not been touched since May 2021 and is almost certainly broken against Steam's late-2023 refresh-token auth ([topic listing](https://github.com/topics/steam-comment-bot)). The only broader-engagement successor project with a real pulse, **zevnda/steam-game-idler** (801 stars, Tauri + Next.js, actively updated through Nov 2026), targets card farming and achievements and ships no comment feature ([zevnda/steam-game-idler](https://github.com/zevnda/steam-game-idler)). Within the surrounding ecosystem the Node.js bots stand on **DoctorMcKay's `steam-user` + `steamcommunity` + `steam-session` trio** (MIT, 1.1k stars on steam-user), the only libraries that wrap Steam's HTML community endpoints for comments, likes, and follows; the .NET world runs on SteamKit2 (LGPL-2.1, needs .NET 8.0+) and Go/Python ports target the binary CM protocol without covering community pages ([steam-user](https://github.com/DoctorMcKay/node-steam-user); [SteamKit2](https://rust-digger.code-maven.com/src/steam-language-gen-0.1.4/assets/SteamKit/readme.md)). The upshot for a desktop rewrite: staying in the Node ecosystem is not merely convenient, it preserves the only mature library layer that speaks to the profile-engagement surface.

### The architectural pattern worth cloning is npm-prefix plugins over a chat bridge

3urobeat's bot runs one "main" account as a control surface in Steam Chat, with a plugin system that **dynamically loads npm packages whose name starts with `steam-comment-bot-`**; the official plugin set already includes `steam-comment-bot-discord-plugin`, `steam-comment-bot-rest`, and `steam-comment-bot-webserver`, all listed in the bot's `package.json` ([plugin docs](https://github.com/3urobeat/steam-comment-service-bot/blob/beta-testing/docs/wiki/creating_plugins.md); [package.json](https://github.com/3urobeat/steam-comment-service-bot/blob/master/package.json)). Storage is `@seald-io/nedb` (embedded JSON), HTML scraping is `cheerio`/`htmlparser2`, and QR login + token rotation came in v2.12.1 with the move to `node-steam-session` ([release 2.12.1](https://newreleases.io/project/github/3urobeat/steam-comment-service-bot/release/2.12.1)). ArchiSteamFarm converges on a nearly identical model — plugin system, embedded Kestrel web server as IPC, Vue-based ASF-ui served from the daemon ([ASF IPC wiki](https://github.com/JustArchiNET/ArchiSteamFarm/wiki/IPC)) — which means the "headless daemon + swappable web UI" pattern is already validated by the single largest Steam-automation project in existence.

## The commercial market sells through Discord bots, not dashboards

The branded Steam-engagement storefronts cluster around a half-dozen "boosting-service"-style domains (boosting-service.com, boosting-service.cloud, imbaboost.com, freehourboost.com, smmsem.com) plus Steam-group storefronts like **Boost Comments LLC** (60 comments for €5, 1,000 for €40, 5,000 for €80, plus €30–€60/month comment subscriptions ([Boost Comments LLC](https://steamcommunity.com/groups/boostcommentsllc))) and freelancer gigs on PlayerAuctions and Fiverr ([PlayerAuctions 1,000 comments](https://www.playerauctions.com/steam-boosting/296457074p!1000-steam-comments--no-vac-/); [Epic NPC $1/1K listing](https://www.epicnpc.com/threads/%F0%9F%8E%AF-steam-profile-comments-1k-1-no-vac.2201584/)). Workflow is uniform and primitive: a web order form or a Steam-group DM feeds a Discord bot that executes against the supply pool. **None of the sourced providers expose a self-serve dashboard or public API**, none ship a desktop client, and Trustpilot carries repeated non-delivery complaints — one buyer paid 19 USDT for 1,000 comments on boosting-service.cloud and got nothing ([Trustpilot](https://ca.trustpilot.com/review/boosting-service.cloud)), another lost a 200-comment order on boosting-service.com with "exit scam" accusations going back to 2020 ([Trustpilot](https://uk.trustpilot.com/review/boosting-service.com)). The pricing spread is telling: **Epic NPC resellers sell at ~$1 per 1,000** while branded storefronts price at ~**€40 per 1,000** — a 40× markup that generalist SMM panels (Peakerr, JustAnotherPanel) do not match because they don't carry Steam at all, instead concentrating on Instagram/TikTok/YouTube/Telegram ([Peakerr press release](https://www.barchart.com/story/news/31827354/peakerr-launches-one-of-the-most-accessible-and-affordable-smm-panels-worldwide)). Supply quality is opaque; every Steam-specific SKU brags only "No VAC" rather than account age or level, which implies botted inventory ([PlayerAuctions No-VAC tag](https://www.playerauctions.com/steam-boosting/296457074p!1000-steam-comments--no-vac-/)), while the 40× premium plausibly buys aged/L2+ accounts at the top end. The **clear white space**: a polished local client that bundles profile comments + screenshot/artwork likes + follows + group joins + Workshop-vote targeting, URL-paste targeting, rate pacing, and a credential vault — exactly what 3urobeat already partially does but without anyone shipping a desktop UI.

## Modern Steam auth is captcha-free but orbits the maFile

Steam's 2023 overhaul replaced the legacy RSA + password + captcha login with the gRPC-style `IAuthenticationService` interface, and every current bot library (node-steam-session, SteamKit2, python-steam, steamguard-cli) is a wrapper around it: the client calls `GetPasswordRSAPublicKey` → `BeginAuthSessionViaCredentials` (password RSA-encrypted) → `UpdateAuthSessionWithSteamGuardCode` or `UpdateAuthSessionWithMobileConfirmation` → polls for a refresh token → trades it for short-lived access tokens and `steamLoginSecure` web cookies ([node-steam-session](https://github.com/DoctorMcKay/node-steam-session)). A third-party Go client confirms that **"a captcha aborts the function"** in the new flow rather than returning a solvable image — Steam either issues a Guard challenge or hard-aborts ([pkg.go.dev escrow-tf/steam](https://pkg.go.dev/github.com/escrow-tf/steam/api/auth)) — and **2captcha and anti-captcha publish no Steam-specific task type**, so the ecosystem has quietly stopped treating captcha as a solvable problem ([scrapfly captcha roundup](https://scrapfly.io/blog/posts/best-captcha-solving-api)). Refresh tokens are community-reported to live ~200 days and node-steam-user auto-renews them in v5; the standard pattern on `LoggedInElsewhere` kicks is to back off 30s–5min and re-logon with the stored token ([dev.doctormckay topic 4228](https://dev.doctormckay.com/topic/4228-login-via-refresh-token); [v4→v5 migration](https://github.com/DoctorMcKay/node-steam-user/wiki/v4-%E2%86%92-v5-migration-guide)). Steam Guard Mobile is **two HMAC-SHA1 secrets with totally different roles**: `shared_secret` drives the 30-second TOTP login code, and `identity_secret` signs the per-request confirmation key submitted to `steamcommunity.com/mobileconf` as `GET /ajaxop?p={device_id}&a={steamid64}&k={HMAC}&t={time}&m=android&tag={conf|allow|cancel}`, with `device_id` formatted as `android:<UUID v4>` ([DoctorMcKay topic 1000](https://dev.doctormckay.com/topic/1000-shared-secret-and-identity-secret); [libr2fa](https://docs.rs/crate/libr2fa/latest/source/src/steam/steam_key.rs); [node-steamcommunity CConfirmation wiki](https://github.com/DoctorMcKay/node-steamcommunity/wiki/CConfirmation)). **Comment posting itself does not go through `mobileconf`** — only login does — which is why a comment/like/follow bot that never trades can get by with just `username:password:shared_secret` rather than a full maFile ([3urobeat config_doc](https://github.com/3urobeat/steam-comment-service-bot/blob/master/docs/wiki/config_doc.md)). The on-disk interchange format is universal: every serious bot (ASF, SDA, steamguard-cli, WinAuth) ingests Jessecar96's SDA JSON maFile unchanged, so a desktop port inherits a zero-cost import path ([ArchiSteamFarm 2FA wiki](https://github.com/JustArchiNET/ArchiSteamFarm/wiki/Two-factor-authentication-fr-FR); [SDA](https://github.com/Jessecar96/SteamDesktopAuthenticator)).

## Rate limits bite at the IP more than the account

Valve publishes no numeric limits, and the community consensus — codified in 3urobeat's error documentation — is that Steam enforces at least three distinct caps. **Per-IP cooldowns** return HTTP 429 (one operator saw 429s on `getUserInventoryContent` after "maybe 20-30 times" per IP ([dev.doctormckay topic 4045](https://dev.doctormckay.com/topic/4045-getting-rate-limited-on-pc-while-bots-are-running-with-proxies/))); **per-account per-section cooldowns** return "posting too frequently" with a reported ceiling near **200 comments per account per rolling 24 hours**, and a burst cooldown that trips after ~10 comments in a minute ([Steam forum 2018](https://steamcommunity.com/discussions/forum/1/1698293255129101037); [Steam forum 2021](https://steamcommunity.com/discussions/forum/1/3113648183775065525)); **friend-request caps** of ~10/day or ~30/week before block, with ~30-day recovery anecdotally ([Steam forum](https://steamcommunity.com/discussions/forum/7/1471967615872532456)). The $5 limited-account gate is a harder wall: limited accounts cannot comment on non-friends, cannot add friends, cannot upvote/downvote, and cannot comment in groups ([3urobeat steam_limitations](https://github.com/3urobeat/steam-comment-service-bot/blob/master/docs/wiki/steam_limitations.md)). 3urobeat's bot bakes in four knobs that map directly to these limits: `requestDelay=15000ms`, `requestCooldown=5min`, `botaccountcooldown=10min`, and `randomizeAccounts=false`, with `quotes.txt` rotating comment text to defeat duplicate-content detection ([config_doc](https://github.com/3urobeat/steam-comment-service-bot/blob/master/docs/wiki/config_doc.md)). On top of that, **node-steam-user's default `machineIdType` derives a unique machine ID from the account name**, so each bot account gets a distinct fingerprint without extra work — Valve's known detection surface collapses to IP, machine ID, timing, and content similarity ([steam-user README](https://cdn.jsdelivr.net/npm/steam-user@5.3.0/README.md)).

The mitigation is proxies, and the ecosystem converges on **HTTP proxies passed via `proxies.txt`** with accounts round-robined across them; 3urobeat's wiki recommends **one proxy per ~3 accounts for mixed workloads ($1/month for 33 proxies covers ~100 accounts)**, and jumps to 1:1 for heavy comment/vote use ([adding_proxies wiki](https://github.com/3urobeat/steam-comment-service-bot/blob/master/docs/wiki/adding_proxies.md)). ArchiSteamFarm only got proper per-bot WebSocket proxying in 6.1.7.4 via `WebProxy`/`WebProxyUsername`/`WebProxyPassword`; pre-6.1.7.4 users needed the third-party `SteamKitProxyInjection` plugin ([ASF 6.1.7.4](https://newreleases.io/project/github/JustArchiNET/ArchiSteamFarm/release/6.1.7.4); [SteamKitProxyInjection](https://redirect.github.com/ezhevita/SteamKitProxyInjection)). Residential/ISP pools (IPRoyal, 922S5, Bright Data, Webshare) are folklore-preferred once datacenter CIDRs are banned but no Valve policy confirms this; SOCKS5 is not first-class in 3urobeat's docs even though node-steam-user supports it via `socks-proxy-agent`. Account warming is also folklore — no Valve-documented schedule exists — but the minimum-viable warmed account is >$5 spend, Steam Guard Mobile attached, a populated profile, and at least one game owned; without these the account is "limited" and gets throttled harder ([3urobeat steam_limitations](https://github.com/3urobeat/steam-comment-service-bot/blob/master/docs/wiki/steam_limitations.md)). On a community ban — which operators treat as burn-and-replace — automated wipes of recent content are common and appeals through Steam Support are slow and opaque ([Steam Suggestions forum](https://steamcommunity.com/discussions/forum/10/3722818378188302327)).

## Electron with the current Node engine is the shortest desktop path

The desktop-framework trade-off is sharper than it first appears. **Electron** costs ~85–270 MB bundled and ~128–168 MB idle RAM for a single window ([betterstack Tauri vs Electron](https://betterstack.com/community/guides/scaling-nodejs/tauri-vs-electron-vs-deno-vs-electrobun.md)), but it **runs steam-user/steam-session unchanged in the main process**, handles auto-update via `electron-updater` on NSIS (Windows) and Squirrel.Mac (macOS), and ships the richest tray/notification/autostart ecosystem ([electron-builder auto-update](https://www.electron.build/docs/features/auto-update); [Electron Tray docs](https://electronjs.org/docs/latest/api/tray)). The gotchas are specific but known: `.node` native modules cannot load inside ASAR archives and must be `asarUnpack`-ed, and `@electron-forge/plugin-auto-unpack-natives` or electron-builder's default handles that for the bot's transitive deps like `sqlite3`/`bcrypt` ([Electron asar docs](https://electronjs.org/docs/latest/tutorial/asar-archives); [electronforge docs](https://www.electronforge.io/config/plugins/auto-unpack-natives)). **Tauri 2** drops the shell to ~1 MB and idle RAM to ~42 MB with a WebView2/webkit2gtk frontend, but a Node-sidecar architecture is required (via `bundle.externalBin`, spawned through the shell plugin), and **Tauri does not kill sidecars on exit** so lifecycle management is manual ([Tauri v2 sidecar docs](https://v2.tauri.app/learn/sidecar-nodejs/); [DEV: Bundling a CLI binary](https://dev.to/chenxxpro/bundling-a-cli-binary-as-a-tauri-v2-sidecar-architecture-and-lessons-from-building-moonproxy-21n3)). Crucially, `pkg` cannot bundle native `.node` modules loaded via dynamic paths, so Bun's `--compile` or shipping stock Node + source tree are the only reliable sidecar strategies — and once you add a bundled Node binary plus the ~150 MB `node_modules` tree as Resources, **Tauri's "tiny" advantage largely evaporates** ([Tauri sidecar docs](https://v2.tauri.app/learn/sidecar-nodejs/)). The one Steam-ecosystem exemplar for a native rewrite is **Watt Toolkit (Steam++)**, C#/Avalonia with YARP reverse-proxy and local authenticator, but that path would mean rewriting the bot on SteamKit2 and giving up the only mature community-endpoint library ([SteamTools README](https://redirect.github.com/BeyondDimension/SteamTools/blob/develop/README.en.md)).

A third option deserves equal weight: the **ASF-ui pattern — a local web server inside the existing Node process plus a browser-opened dashboard** — is already underway in the 3urobeat ecosystem via `steam-comment-bot-webserver` (listed as a dependency) and DerDeathraven's REST API plugin exposing `localhost:4000/rpc/${Class}.${MethodName}` with a Vue frontend at `localhost:5123` ([package.json](https://github.com/3urobeat/steam-comment-service-bot/blob/master/package.json); [DerDeathraven REST plugin](https://github.com/DerDeathraven/steam-comment-bot-rest-api); [frontend](https://github.com/DerDeathraven/steam-comment-service-bot-frontend)). It costs zero code signing, zero SmartScreen, zero notarization — but loses tray, autostart, native notifications, and the "double-click to install" UX for non-technical buyers. Code signing in 2026 is cheaper than it was: **Microsoft now explicitly lists EV certs as "no longer recommended for SmartScreen"** since EV no longer grants instant reputation, and Azure Trusted Signing at ~$9.99/month plus Apple Developer at $99/year puts the cross-platform budget at ~$220/year ([Microsoft code-signing-options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options); [ToDesktop blog](https://www.todesktop.com/blog/posts/windows-apps-psa-ev-certs-do-not-grant-immediate-reputation-anymore); [flaviocopes](https://flaviocopes.com/apple-developer-free-vs-paid/)). The multi-account UX convergence across every observed Steam tool (ASF-ui, SAM, Watt Toolkit) is **one dashboard window with virtualized account cards plus a single tagged log panel** (xterm.js is the standard live-log component), *not* one window per account — which would push an Electron app into 300–500 MB territory fast ([ASF IPC wiki](https://github.com/JustArchiNET/ArchiSteamFarm/wiki/IPC); [xterm.js](https://unpkg.com/@xterm/xterm@6.0.0/README.md)).

## Conclusion

The research reveals an unusually clean competitive picture: the open-source leader has no desktop fork, the commercial storefronts run on 2010s-era Steam-group + Discord-bot plumbing with no self-serve dashboard or API, and generalist SMM panels don't carry Steam at all. The technical risk in a desktop build is not Steam's defenses — the modern `IAuthenticationService` flow is well-understood and captcha-free, maFile ingestion is a solved interchange, and rate limits are a configuration problem that 3urobeat's existing `requestDelay`/`botaccountcooldown` knobs already address — but framework choice and lifecycle discipline around a persistent multi-account Node engine. Electron with the engine in-process is the lowest-friction path that preserves the McKay library stack (which no other language ecosystem matches for community endpoints); Tauri-plus-Node-sidecar wins on idle memory only if the dashboard carries its weight and you accept manual sidecar supervision; the ASF-ui-style local-web-server path is the fastest MVP but concedes the native UX that would differentiate this product from both the Vue frontend already in progress and the Discord-bot storefronts. The strategic insight is that **the first polished desktop client in this niche also inherits the only mature "likes/favs/follows" library stack in the ecosystem**, because competitors are either Node CLI projects that nobody has wrapped or .NET projects (ASF, Watt Toolkit, SteamKit2 clones) that would need to re-implement the community HTML endpoints from scratch to even enter this category.
